# Engineering of intelligence: hypothesis explorer

A standalone Astro prototype for exploring the research hypothesis in [assembly_hypothesis.md](../assembly_hypothesis.md). It follows the direct-manipulation style of the local ECE732 Astro interactives, but it is deliberately a separate project.

```bash
npm install
npm run dev
npm run build
```

The UI uses synthetic, uncalibrated default anchors (100M parameters; 82% ordinary-slice and 45% tail-slice coverage). All calculated coverage percentages are *hypothetical task-score proxies*, not actual driving performance or probability of safety. The separate Chinchilla/Gopher panel contains sourced language-benchmark measurements. The model's elasticities, data ceilings, feature-retention rule and uncertainty factor are explicit conjectures in `src/lib/model.mjs`. The anchor refers to the fixed default reference configuration, and changing the scenario controls extrapolates from that reference. Absolute model-size numbers should only be used after replacing the anchor and curve assumptions with measurements from a named task and architecture family. Even then, the result would remain a within-family forecast, not a universal minimum.

The hardware pane evaluates a chosen dense-transformer work and weight/KV traffic scenario. Weight storage is a representation floor under the entered precision. The shown latency is an optimistic roofline estimate under entered **effective** compute and bandwidth, excluding framework overhead, sensor transfer, preprocessing, attention-specific work, activations beyond the simple KV input, and action execution. It must be measured on target hardware before use.

The prototype's key question is whether a task-conditional reuse/assembly descriptor predicts held-out scaling curves better than ordinary compression, task-aware MDL and pilot-only baselines. The [research note](../assembly_hypothesis.md) specifies counterexamples and falsifiers. The app keeps cited Chinchilla/Gopher language results in a separate panel because no comparable task-specific visual-avoidance model sweep has been collected. Those two published points are not a parameter-only scaling curve and have no known information-theoretic performance limit.

## Reference-function ladder (2026-09-28)

`/ladder` shows the first measurements:
- **What was fitted:** MLPs of widths 2–256 fitted to known functions (PID, clipped PID, pendulum, cart-pole, double pendulum, 50–800 ms flow maps, and the pendulum from rendered 24×24 frames).
- **What it reports:** the smallest size and data set reaching each fit threshold, and bits kept after quantization.
- **Source data:** `src/data/reference_ladder.json` is written by `../experiments/reference_ladder.py`. Captions and findings are in `src/data/reference_ladder_notes.json`.
- **Write-up:** [../reference_ladder_findings.md](../reference_ladder_findings.md).

## Intelligence budget (2026-09-28)

`/budget` presents the condensed hypothesis from [../intelligence_budget.md](../intelligence_budget.md):
- **The idea:** every input is a supply of, or demand for, bits. One task curve `K(ε)`, about 2 bits stored per parameter, and hardware, data and evidence budgets reduce to five dimensionless numbers and a margin in dB.
- **Calculator:** `src/lib/budget.mjs`. Its six presets are illustrative anchors; each preset's note says which values are sourced.
- **Ladder data:** `src/data/budget_ladder.json`, generated by `../build_budget_ladder.py`. It has 55 systems, each with a verification status (`verified`, `atlas-verified`, `documented`, `secondary`, `definitional`).
- **Static charts:** the task-description ladder, same-task description series, the intrinsic-dimension ladder, supervision bits per example, the α/β exponent test, and a NASA observation-gap table.

## Expanded research atlas (2026-09-27)

The site now has four routes:

- `/`: the original explicitly hypothetical visual-task and hardware calculator.
- `/atlas`: 139 published TorchVision 0.17 weight configurations on separate ImageNet, COCO detection, COCO/VOC segmentation and Kinetics panels; an observed best-of-parameter-budget frontier; a simple model-work throughput screen.
- `/cases`: 46 AVOIDDS slice scores, six NASA ranging sorties, AirTrack, Tesla HW3/AI4/AI5, NVIDIA edge hardware, and named face-verification cases.
- `/method`: a variable-by-variable estimation guide and a testable best-achievable-frontier formulation.

The 139 weight observations are generated reproducibly by `../extract_torchvision.py` from the official pinned TorchVision 0.17 HTML snapshot stored in ignored `../out/sources/`. That script requires BeautifulSoup 4. It excludes the VGG16 feature-only weight with `nan` benchmark accuracy. The output JSON embeds the snapshot SHA-256 and per-weight source URL/row locator. Cross-domain observations and source status are in `src/data/cross_domain.json`; details and original-source inspection scope are in [cross_domain_findings.md](../cross_domain_findings.md).

**Frontier interpretation:** the best published score at or below P parameters is a lower bound on what is attainable with that budget. It is not a proven upper limit on what a better architecture or training process could achieve. The model-work pane computes `GFLOPs/input × streams × FPS ÷ 1000` as required TFLOP/s; it requires an effective throughput measurement at compatible precision and omits the rest of the deployment pipeline. Vendor INT8/sparse TOPS are displayed separately from those FP work figures.

The AVOIDDS slices overlap and the six NASA sorties share a single optical setup. These points are discussion cases, not independent samples of a universal scaling relationship. Tesla AI5 is plotted only as a relative, forward-looking target because the cited Tesla investor update does not disclose an AI4 absolute baseline.

The exact nested-risk decomposition and the corrections to the focused mathematical-source scout are in [frontier_gemini_triage.md](../frontier_gemini_triage.md).
