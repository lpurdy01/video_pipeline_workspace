# Resource package and release

Planned standalone GitHub companion package. No repository created or publication performed at this setup stage.

| Public artifact | Working source | Readiness requirement |
|---|---|---|
| README and concept map | Project brief + reviewed architecture | Accurate scope and stable title |
| Whitepaper Markdown/HTML/PDF | `resource_composition/` | Same reviewed manuscript revision and inspected figures |
| Evidence guide and bibliography | Source/claim registry | Primary locators, inspection limits, dissent and freshness |
| Worked case / optional demonstration | `assurance/` | Reproduction steps, assumptions and no implied real-world qualification |
| Agent brief and critique guide | Wiki synthesis + review policy | Read order, open issues and evidence boundaries |
| Selected verification records | `verification/` | Input hashes and reviewer provenance; no credentials/private data |
| CITATION, license, attribution | New release metadata | Distinguish original work from third-party rights |
| Video links and launch copy | Reviewed delivery and launch draft | Exact title, version, captions and public link accessibility |

Build exports to ignored `out/package/` from an allowlist. Do not recursively copy the workspace. Do not publish human voice sources, detailed timing, licensed PDFs, raw API logs or unpublished private commentary.

The release manifest must pin exact source revisions and output hashes, review dispositions, known limitations, generation tools/versions and an as-of date. Recheck fast-changing regulatory claims before script lock and again before release. Verify links anonymously. The earlier project's retrospective shows why a stale launch checklist must not override the exact final build record.

Choose public destination, name and license after the argument and package are reviewable. Do not reuse the old package's MIT declaration for third-party source material.
